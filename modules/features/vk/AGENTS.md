# Agent instructions for `$HOME/Vaults`

This file is regenerated by `vk` on every `serve-all` rebuild (and kept
in sync whenever `apply-dots` upgrades `vk`) - edits here are lost on
the next rebuild. Put anything you want to persist in
`memory-bank/` (see below) instead.

`$HOME/Vaults` holds every vault as a sibling subdirectory, each one a
self-contained MyST project with its own `myst.yml`. Vaults are meant
to be cross-linked - a relative Markdown link or `{doc}` role from one
vault into a sibling vault is normal and expected, not a mistake.

## Structure shared by every vault

- `materials/`, `records/`, `texts/` - the three note categories. Every
  actual note lives in exactly one of these, flat (no further nesting).
- `assets/` - images and other binary attachments.
- `myst.yml`, `references.bib`, `main.md`, `index.md` - project config,
  bibliography, and the hand-edited/generated landing page.
- `.vk-staging/` - **entirely generated**. Never read it for "the real
  content" and never hand-edit anything inside it; it's rebuilt from
  the authored files on every `vk build`/`watch`/`serve-all` poll and
  discarded freely (`rm -rf .vk-staging` is always safe).
- `explore/` inside `.vk-staging/` - generated navigation (tags,
  recent, orphans, a Mermaid link graph). Also not authored content.
- `AGENTS.md` and `memory-bank/` at each vault's own root - see below.

## Frontmatter conventions (categorized notes only)

- `id` - assigned once when a note is created, then stable forever.
  Never change an existing note's `id`; a rename/move adds the old
  path to `aliases` instead (see below).
- `title` - required for every categorized note.
- `type`, `tags` - `tags` mixes topical tags (used for Related Notes
  scoring) with structural ones; keep structural tags out of the
  topical vocabulary so they don't swamp real relatedness matches.
- `aliases` - previous ids/paths a note has had; only touched by the
  rename/move action below, never hand-maintained.
- `date` - authored date, distinct from the file's own source mtime
  (which drives the generated "recent notes" ordering).

Root/category `index.md`, `main.md`, and any other vault-root page
never need (or get) an `id` - there's nothing to preserve across a
rename and nothing ever `{doc}`-references them by id.

## Editing rules

- **Renaming or moving a note or asset**: always use `vk note`'s
  Rename/Move action, never a raw `mv`. It preserves the note's `id`,
  appends the old path to `aliases`, and rewrites every Markdown/`{doc}`/
  image reference to it across the vault it lives in *and* every
  sibling vault under `$HOME/Vaults` - a raw `mv` silently breaks all of
  that.
- **Links**: plain Markdown links and MyST `{doc}` roles only - `vk`
  vaults don't use wikilink syntax. All rewriting/matching is absolute-
  path based internally but only ever *writes* relative paths back;
  never introduce an absolute filesystem path (especially anything
  under `$HOME`) into vault content.
- **Citations**: add new bibliography entries via `vk import`'s
  Bibentry mode (extracts the key, rejects a duplicate, appends to
  `references.bib`) and cite with native `[@citekey]` syntax - don't
  hand-maintain a separately formatted citation as the primary
  representation.
- **Directives**: Taskwarrior blocks and `{graphviz}` are preprocessed
  only during staging; the raw authored file keeps the directive
  syntax, not its rendered output.
- **Validate before finishing**: run `vk check <vault>` (or
  `vk check all` across every vault) after any edit. It runs a strict
  MyST build plus static checks (frontmatter shape, duplicate ids/
  aliases, unresolved links, missing assets, directive/plugin
  validity) and reports `path:line` diagnostics.

## Persistent agent memory

- **Per-vault**: `<vault>/memory-bank/` - durable, agent-relevant
  context specific to that one vault (recurring themes, in-flight
  projects, the user's own shorthand/conventions for that vault,
  structural decisions). Seeded once with a stub `README.md`; add
  files freely, they're never overwritten.
- **Cross-vault**: `$HOME/Vaults/memory-bank/` - anything spanning more
  than one vault, or about the vault collection as a whole (this
  file's own conventions don't need repeating there - only genuinely
  new, durable knowledge).

Both `memory-bank/` folders hold plain Markdown with no frontmatter
required; they're ordinary vault-root content, not staging output, so
they persist across every rebuild.
